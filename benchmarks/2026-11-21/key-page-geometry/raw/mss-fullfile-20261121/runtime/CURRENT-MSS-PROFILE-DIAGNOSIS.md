# Smaller key pages are the next experiment

Test one change in the portable C++17 reference reader. Compare the current **64 KiB × 128** cache for the `keys` file with **16 KiB × 512**. Both allow 8 MiB of key payload per reference handle. The live sample places 514 of 3,446 main-thread observations inside a stream read serving a lower-bound **key-line** probe. It establishes where to experiment. It gives neither bytes transferred nor the better page size. No candidate build or counter run was performed for this diagnosis. ## Cache behavior and scope

Each handle has separate 8 MiB page-payload budgets for keys, offsets and records, plus 4 MiB for FASTA (28 MiB total). The format-2 fixture has 30,066,969 key bytes (459 current pages), 10,498,992 offset bytes and 36,006,536 record bytes. Every miss clears the stream, seeks and requests one whole page, including on the final short page. Hits use the last-page shortcut or the LRU map. An eviction reuses the victim's string buffer. Binary search already caches up to 8,191 validated midpoint keys (up to 56 bytes each, at most 64 bytes per slot) and 4,096 exact lower-bound ranks (keys up to 224 bytes, under 1 MiB total). An uncached midpoint reads an 8-byte offset and visits the associated key line. Successful and unsuccessful searches must still visit the existing boundary rows when required. [Cache and page crossing](/private/tmp/mss-lazy-variantannotation-20261121/src/preservation_core.h:28) · [FASTA](/private/tmp/mss-lazy-variantannotation-20261121/src/preservation_core.h:194) · [Search and reference construction](/private/tmp/mss-lazy-variantannotation-20261121/src/preservation_core.h:373)

The proposed geometry allows four times as many disjoint key-file regions to stay resident and requests one quarter as many bytes per miss. That mechanism applies to distinct keys in any sufficiently large index. Dense sequential searches may favor wider reads, and long aliases can cross more pages. The payload cap stays fixed. At capacity the candidate adds at most 384 string/map entries and 384 LRU list entries per handle, plus the implementation-dependent increase in hash buckets and allocator overhead. Total process RSS must be measured. The ordinary R interface, binary index format, search comparisons, record and FASTA cache sizes, and stream API all retain their current behavior.

## One controlled comparison

1. In a candidate checkout, change only the `keys` member initializer in `Reference` to use 16,384 bytes and 512 pages. Reuse the existing standalone `lookup_parity.cpp` and its `MSS_LOOKUP_COUNTERS` build. Its built-in 3,000-key shuffled pressure fixture fits the current key cache, so keep it as a regression control. For the geometry comparison add a test-only mode to the same driver that opens the frozen matched index and FASTA. No change to the R API or on-disk index is needed.
